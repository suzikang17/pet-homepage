phased-autonomous-build

name: phased-autonomous-build

description: Use when building or migrating a large multi-phase software project mostly hands-off — orchestrate each phase as plan → critique → implement/review/fix → verify via the Workflow tool, gated on a REAL automated test signal. Use when the user opts into heavy multi-agent orchestration (e.g. says “ultracode”) AND the project can build/test headlessly from the CLI.

Lives at ~/.claude/skills/phased-autonomous-build/SKILL.md — global, so it’s available in every project.

Run a large build as a sequence of self-verifying phases, each orchestrated by the Workflow tool, so a human can step away and come back to working, reviewed code. This is the pattern that produced a 144-test iOS app v1 across ~7 background workflow runs.

When to use

  • A multi-phase build or migration where phases are sequential and each is independently shippable (e.g. an app from scratch, a framework migration, a broad refactor).
  • The user has explicitly opted into multi-agent orchestration — the Workflow tool requires this (the “ultracode” keyword, or a direct ask).
  • There is a real automated pass/fail signal: a test runner, type checker, or build. Without one, do NOT run autonomously — agents will ship confident, broken code.

Preconditions — verify these FIRST

  1. Headless toolchain. You can build AND test from the CLI with zero GUI steps. For iOS this specifically means xcodegen (generate the .xcodeproj from a project.yml — an agent cannot create one through the Xcode GUI), plus xcodebuild + installed simulators. For web: the test/typecheck/lint/build CLIs.
  2. Permissive execution. Tool calls run without per-call approval (or the human is present). Otherwise autonomy stalls on permission prompts every few seconds.
  3. A spec and a plan. Brainstorm and write the design first (superpowers:brainstorming → superpowers:writing-plans). Agents that transcribe-and-verify a precise plan are far more reliable than agents that free-solve.

The per-phase loop (one Workflow script per phase)

Plan      → Opus agent writes a bite-sized TDD plan to disk (exact code per step,
            exact verify commands). A second Opus CRITIC gates it; revise until clean.
Implement → for each task IN SEQUENCE (they share git state): a cheap implementer
            writes the failing test → implements → runs the real test → commits.
Review    → an adversarial reviewer checks each task's diff for spec-compliance AND
            quality; a fix-loop runs until there are no blocking findings.
Final     → one Opus pass over the whole-phase diff.

Run one Workflow per phase, in sequence. Between phases, re-run the full test suite yourself before launching the next — that independent checkpoint is what keeps the whole thing honest (it once caught a primary screen that was built + unit-tested but never wired into navigation).

Model routing

Planner / critic / final-review = most capable (Opus). Implementers transcribing exact plan code = cheapest tier. Reviewers = mid-tier scaled to diff size. Always set the model explicitly.

Hard-won gotchas

  • Sequential, not parallel, when sharing git state. Tasks that build on each other’s commits must await each other; parallel implementers on one working tree conflict.
  • args does NOT reliably thread through Workflow({scriptPath}). Hardcode the phase parameters in the script’s default values and edit them per phase. (A whole phase silently re-ran the wrong work — ~2M wasted tokens — because args fell back to the default.)
  • Pin the simulator OS (name=iPhone 16,OS=18.2) — a bare device name is ambiguous and rejected by xcodebuild.
  • Exclude tooling/state dirs (.omc/, .build/, etc.) from the build’s source glob, or you get “Multiple commands produce …” duplicate-resource errors.
  • DEVELOPMENT_TEAM is the team ID, not the cert ID. Put it in project.yml so it survives xcodegen generate; otherwise it reverts every regeneration and the human re-sets it by hand.
  • Trust the build, not the editor. Background SourceKit/LSP diagnostics (“Cannot find type X in scope”) are false alarms when the generated project isn’t loaded in the IDE — the xcodebuild/tsc result is ground truth.
  • Verify before claiming done. Re-run the suite; one flaky test-host launch reported TEST FAILED with zero real failures. Don’t trust a single run.
  • CloudKit/offline-first helps testability. In-memory Core Data + fakes for notifications/network = fast, self-contained, headless tests that don’t need a backend or signed build.

Cost awareness

This is token-heavy — a real v1-app run was ~180 subagents and ~10M subagent tokens. Only run it on explicit opt-in. The single biggest waste is re-running a phase by mistake, so confirm the script targets the intended phase before launching (read back the defaults).
